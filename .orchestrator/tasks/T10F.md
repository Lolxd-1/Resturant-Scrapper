# T10F: Fix three defects found by T10 (sheet clearing, per-restaurant item load, stuck "blocked" flag)
Wave: 11 · Deps: T10 · Risk: med · Model: sonnet

## Goal
PENDING sheets never inherit READY values; adding a live menu to the engine costs milliseconds, not a full pool reload; a Zomato block in one job does not disable live search for every later job.

## Context
Found by the T10 executor (.orchestrator/reports/T10.md, Concerns 1, 2, 4):
1. `studio/sheets.py` `_clear_rows` and `_write_rows` call `ws.cell(row=i, column=c, value=None)`; openpyxl ignores `value=None` in `cell()`, so nothing is cleared and None values are never written. A PENDING row without a photo showed a READY row's photo URL.
2. `studio/store.py:114` `items_for_restaurant` filters `self.all_items()` (rebuilds the whole 137k-item list after each upsert) -> ~0.5 s per `Engine.add_menu`.
3. `studio/pipeline.py`: `engine.blocked` is set on ZomatoBlocked and never reset.

## Steps
1. sheets.py: every cell write in `_write_rows` and `_clear_rows` uses `ws.cell(row=i, column=c).value = v` so None really clears. Keep the single-load design.
2. store.py: `items_for_restaurant(res_url)` runs one SQL query joining items and restaurants `WHERE items.res_url = ?` (canonical url) and builds PoolItems directly; it must NOT call or invalidate-then-rebuild `all_items()`. `upsert_menu` may still invalidate the all_items cache (that is fine; all_items is only rebuilt when someone calls it).
3. pipeline.py: `engine.blocked` becomes a timestamp-based state: add attribute `blocked_until: float = 0.0`; on ZomatoBlocked set `blocked_until = time.monotonic() + 1800` and keep `blocked` as a read-only property returning `time.monotonic() < blocked_until`. At the start of each run_job log "Live search paused for N more minutes (Zomato limited this PC)" when still blocked.
   Make sure Engine.add_menu does not call `store.all_items()`.

## Test cases
- TC1 (RED first): build_outputs with results [ready A with hosted_url "https://i.ibb.co/a.jpg", needs_photo B (no url, price 50, description "")] -> PENDING row 2 is B and its P, I cells are empty (None); READY row 2 is A. Also: a READY file built from 1 ready row after a PENDING-first ordering keeps no stale values (row 3 column C empty).
- TC2: store with 20,000 items across 200 restaurants (fast executemany in the test) -> after one more upsert_menu, items_for_restaurant(url) returns only that restaurant's items and takes < 50 ms; all_items() is not called (monkeypatch it to raise).
- TC3: engine blocked in job 1 (403s) -> job 2 within the window skips live search (no /order requests) and logs "Live search paused"; after monkeypatching time.monotonic forward 1801 s, job 3 performs live search again.
