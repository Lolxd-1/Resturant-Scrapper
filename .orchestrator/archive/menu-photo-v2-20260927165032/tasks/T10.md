# T10: Pipeline engine (run_job) + offline end-to-end tests
Wave: 10 · Deps: T02-T09 · Risk: high · Model: opus

## Goal
`studio/pipeline.py` runs a whole vendor job: read menu -> detect own/chain restaurant -> match against the pool -> live whole-Zomato search for unresolved dishes (budgeted, multi-city) -> vision verification -> download -> upload -> build sheets, emitting progress events, checkpointing to the job dir, never aborting on a single dish's failure.

All building blocks exist: studio/menu.py, text.py, lexicon.py, zomato.py, store.py, matcher.py, imaging.py, vision.py, hosting.py, sheets.py. Read `.orchestrator/PLAN.md` (Contracts: pipeline) and the Goal/ACs AC1, AC5-AC7, AC10. This module wires them; do not duplicate their logic.

## Contracts
- Produces: `JobOptions` (dataclass, fields per PLAN), `class Engine` (`__init__(self, store: PoolStore, vision: Vision, http: Http)`; attributes `store`, `vision`, `http`, `client: ZomatoClient`, `index: PoolIndex`, `blocked: bool`; method `add_menu(self, menu: RestaurantMenu) -> int` = store.upsert_menu + index.add(store.items_for_restaurant(menu.url))), `build_engine(settings: Settings | None = None, *, allow_download: bool = True, on_status: Callable[[str], None] | None = None) -> Engine` (real Http, PoolStore(pool_db_path()), ensure_seeded(SEED_POOL_PATH), load_vision(models_dir())), `run_job(engine, menu_path, job_dir, opts, *, uploader, on_event=None, cancel=None) -> dict`, `new_job_id(vendor: str) -> str` (`YYYYMMDD-HHMMSS-<slug>`), `load_job(job_dir: Path) -> dict`, `list_jobs(output_dir: Path) -> list[dict]` (newest first, each job.json content plus "id"), `class JobCancelled(Exception)`, `infer_category(q: DishQuery) -> str`.
- Events and job-dir layout exactly as in PLAN Contracts. job.json keys: id, vendor, options (asdict), status ("running"|"done"|"failed"|"cancelled"), stage, created, updated (ISO local time), summary (dict or null), error (str or null), menu_file (file name).

## Steps
1. Setup: job_dir.mkdir; copy menu to `job_dir/menu<ext>` (skip if it is already that file); open log.txt (utf-8, append); `emit(ev)` calls on_event (exceptions swallowed) and appends log lines for "log"/"stage"/"error" events. Write job.json status running.
2. read: read_menu; errors -> status failed, error event with the first error, return summary with total 0. prefix = opts.sku_prefix (sanitized A-Z0-9, max 6) or derive_sku_prefix(opts.vendor). SKU = f"{prefix}-{row:03d}". For each MenuRow: q = parse_dish(name, category, description); category = row.category or infer_category(q). infer_category maps HEAD_GROUP of q.head: drink_glass->"Beverages", hot_cup->"Hot Beverages", dessert->"Desserts", flatbread->"Breads", rice->"Rice & Biryani", curry->"Main Course", bread_snack->"Snacks", pizza->"Pizza", noodle_pasta->"Pasta & Noodles", fried_snack->"Snacks", south->"South Indian", dumpling->"Momos", egg->"Egg Specials", grill->"Starters", plate->"Thalis", bowl->"Soups & Salads", roll->"Rolls & Wraps"; no head -> "Menu". Group rows by q.base_key (size variants share one photo decision); process groups in menu order.
3. source (stage "source"): skip when opts.vendor has < 3 letters. If opts.zomato_url -> fetch_menu -> kind "own". Else for city in ([opts.city] if opts.city in CITIES else ["pune","mumbai","ncr","bangalore"]): sr = client.suggest(vendor, city); if sr.chains -> outlets = client.chain_outlets(sr.chains[0])[:4] -> kind "chain"; else same = restaurants whose chain_key equals chain_key(vendor) or rapidfuzz ratio >= 92; len(same) >= 2 -> chain (first 4); len(same) == 1 and opts.city == city -> "own"; stop at the first hit. Also: if the pool already holds >= 3 restaurants with chain_key == chain_key(vendor), use their items as a chain source without fetching. Fetched menus go through engine.add_menu. Then for every group: `same_dish_menu_match(q, source_items, idf)`; a hit becomes that group's pick with source kind (own/chain) and skips pool matching. Log "Vendor found on Zomato as <kind>: <name> (<n> outlets)" or "Vendor not found on Zomato; using photos from other restaurants".
4. match (stage "match"): for other groups: cands = rank(q, index.retrieve(q), index.idf) minus store.is_bad_image. confident(group) = at least one exact/strong candidate AND (exact/strong candidates come from >= 2 distinct res_url OR the best is exact).
5. search (stage "search"), only if opts.live_search and live_budget_menus > 0 and not engine.blocked: unresolved = groups not confident (combos included). cities = [opts.city] + DEFAULT_SEARCH_CITIES (deduped, only keys of CITIES). Up to 3 rounds; round r uses city slices [0:3], [3:8], [8:20]. For each unresolved group in a round: targets = restaurants from client.suggest(query_text, city) (query_text = main-variant display: name without parentheses, size suffix removed) + client.listing(city, cuisine) for the first 2 cuisines of HEAD_CUISINES.get(q.head, ("north-indian","street-food","fast-food")). Cache suggest/listing results per job (dict keyed by args). New targets = canonical urls with store.menu_fetched_at(url) is None, deduped across the batch; fetch with ThreadPoolExecutor(max_workers=4) until the budget is used; engine.add_menu each; after each batch re-rank every unresolved group and drop newly confident ones. ZomatoBlocked anywhere -> engine.blocked = True, log warning "Zomato is limiting requests from this PC; continuing with photos already found.", end the stage. Progress = processed groups / unresolved.
6. verify (stage "verify"): per group take top 8 candidates (own/chain pick: just that candidate). Thumbs via imaging.fetch_thumb with ThreadPoolExecutor(max_workers=6); embedding cache key = img_url (store.get/put_embedding). Candidates whose thumb fails are dropped and store.mark_bad_image(url, "thumb failed").
   - vision.available: food = food_ok, head = head_ok(q.head), cons = consensus(vecs, weights=text scores), ts = text_sim(vecs, q.display); drop food False or head False; final = 0.60*text + 0.20*cons + 0.20*ts; for source "pool"/"live" candidates whose chain_key has >= 5 restaurants in the pool (big brand) and the vendor is not that brand: final -= 0.03.
   - not available: final = text; drop "close" tier.
   - strictness "strict": drop close. "balanced": keep close only when no exact/strong survives AND vision.available AND cons >= 0.5.
   - Sort by (tier rank, final desc). Distinct images: a per-job dict img_url -> base_key; if the best's img is already used by another base_key, take the next surviving candidate of the same tier if any.
   - Record pick + up to 4 alternates (dict fields per models.DishResult.alternates) + confidence = round(final, 3) + tier + source + item/restaurant fields. No surviving candidate -> needs_photo with reason: variants empty -> "Name is not in English letters — add an English name"; combo -> "Combo dish — ask the owner for a photo of the combo"; had candidates before vision/strictness -> f"Only uncertain matches found (best: {item} @ {restaurant})"; else "Not found on Zomato".
   - Write results.json (list of dish_result_to_dict) after this stage.
7. photos (stage "photos"): per group with a pick: imaging.fetch_full; failure -> mark_bad_image and try the alternates in order; all fail -> needs_photo "Photo download failed". Write the JPEG to images/<SKU>.jpg for EVERY row in the group; local_image = "images/<SKU>.jpg"; image_size "WxH". Emit a "dish" event per row.
8. upload (stage "upload"): if opts.upload: uploader None -> every photo row gets status "error", reason "No ImgBB API key saved. Add one in Settings." For each group, one upload call (bytes identical across the group -> the uploader's sha cache dedupes); UploadError -> the group's rows "error" with the message; if the message starts with "No ImgBB API key" stop uploading further groups (same error for the rest). Checkpoint results.json after every group. If not opts.upload: skip (dry run).
9. Final statuses per row: photo AND (hosted_url or not opts.upload) AND price -> "ready"; photo but price None -> "needs_price" (reason "Add a price, then upload"); status "error" stays; else needs_photo.
10. build (stage "build"): sheets.build_outputs(results, TEMPLATE_PATH, job_dir, opts.vendor, vision_on=engine.vision.available). Summary dict per PLAN (coverage = rows with a photo / total, rounded 3). job.json status done + summary; emit "done".
11. Exceptions: per-group work wrapped so one failure marks that group's rows "error" with a short reason and continues. An unexpected exception outside group work -> status failed, error event, results.json still written. cancel.is_set() checked between groups and batches -> JobCancelled -> status "cancelled", results.json written, outputs built from what exists.
12. Resume: if job_dir/results.json exists at start, load it; in step 7-8 a row whose new pick zomato_img equals the old one AND old hosted_url is set AND the image file exists keeps its old image/hosted_url with no download/upload.

## Test cases (tests/test_pipeline.py; Engine built from FakeSession-backed Http(min_interval=0, sleep=no-op), a tmp PoolStore, FakeVision; uploader = Uploader([ImgbbKey("t","k"*32)], http_post=fake, store=store))
- TC1 end-to-end: pool seeded (store.upsert_menu of synthetic menus) with items matching a 6-row menu (incl. "Cheese Pizza - Small" and "- Large", one row without price, categories "Pizza"/"Beverages"). Result: READY has 4 rows with menu categories in H, PENDING has the no-price row with its photo URL, images/ files exist, both pizza sizes share one zomato_img, job.json status "done".
- TC2 chain: suggest returns a chain_outlets entry; the chain page lists 2 outlets whose menus contain the dish names -> those rows have source "chain".
- TC3 own url: opts.zomato_url set -> source "own" for matching dishes, no suggest call made.
- TC4 live search: empty pool; suggest/listing for pune empty, for mumbai lists a restaurant whose menu has the dish -> row ready with source "live"; the store now contains that restaurant; a second job with a fresh Engine on the same store makes no /order request.
- TC5 blocked: every zomato.com request returns 403 -> job finishes "done", dishes needs_photo, a log event mentions "limiting requests".
- TC6 text-only: NullVision -> a dish whose only candidate is "close" ends needs_photo with "Only uncertain matches"; an exact dish is ready; summary["vision"] is False.
- TC7 resume: run a job, then run_job again on the same job_dir -> the fake http_post (ImgBB) is not called in the second run.
- TC8 distinct images: two different dishes whose best candidates share one image but each has another exact candidate -> different zomato_img.
- TC9 unicode menu (Devanagari name + "₹" in description) -> job done; Devanagari row needs_photo with the English-letters reason; outputs open.
- TC10 no keys: uploader None with opts.upload True -> photo rows status "error" with the Settings message; outputs built.
- TC11 cancel: cancel event set from on_event after the first "dish" event -> status "cancelled", results.json exists.
- TC12 blank categories: menu without categories -> READY column H has inferred values ("Pizza", "Beverages").
- TC13 veg safety: a veg dish with only non-veg pool items -> needs_photo.
