## Important
1. studio/server.py:221-228, studio/sheets.py:187-190 · A failed rebuild is swallowed and the stale sheet is served silently. The common case is the team member having `*_UPLOAD_READY.xlsx` open in Excel: `wb.save` raises PermissionError, `_rebuild` only logs it, and `get_job_file` serves the old file, which Excel still lets others read. · On Windows this is the everyday way a rejected photo stays in the sheet. · Fix: record `rebuild_error` in job.json. If the flag is stale or a rebuild failed, have `get_job_file`/`zip` return 409 "Close the Excel file ... then download again". Clear `rebuild_error` on the next successful rebuild. Retrying the save is optional.
2. studio/brand.py:61-65,74-82; studio/pipeline.py:757-758 · If the OCR brand guard can't load (onnxruntime/RapidOCR import or DLL failure), it disables itself with a single `log.warning`. Nothing reaches job warnings, the UI or REPORT.xlsx. Every photo then skips the Zomato/Swiggy/other-chain branding check, while the UI looks normal. · Branded photos can reach UPLOAD_READY with no signal (priority 1). The vision fallback is surfaced ("Visual check unavailable"); this one isn't. · Fix: add `BrandGuard.available` / `reason`. After `photos()` builds the guard, append a job warning ("Logo check unavailable: ...") if it is disabled. Show it in REPORT Summary next to "Visual check". Consider treating a disabled guard like text-only mode, e.g. rejecting sources from big chains.
3. scripts/setup.ps1:188-196, app.py:44-67 · Fresh-PC gap. `onnxruntime_pybind11_state.pyd` and `onnxruntime.dll` import MSVCP140.dll and MSVCP140_1.dll (checked in .venv). They don't bundle them, and the uv-managed CPython doesn't provide them. This dev PC has them in System32, so the T13 fresh-PC simulation could not catch the problem. On a clean Windows install without the VC++ 2015-2022 redistributable, both CLIP and OCR fail. The app then runs text-only, with the brand guard silently off (see #2). `--self-test` only checks HTTP. · This fails the AC12 "no manual steps" goal and precision on exactly the PCs the launcher targets. · Fix: have `--self-test` / startup import `onnxruntime`. If it fails, print a plain-English message with the VC++ redistributable link (https://aka.ms/vs/17/release/vc_redist.x64.exe) and show it in /api/system status. Adding a new dependency is not needed.
4. studio/pipeline.py:691-693, 787-789; studio/store.py:249-259 · `mark_bad_image` is permanent (no expiry is ever checked) and is also called for transient failures. `fetch_thumb`/`fetch_full` return None after `Http.get` runs out of retries on a connection error or timeout (zomato.py:146-150), and that None is recorded as "thumb failed" / "download failed". A short Wi-Fi drop during verify permanently removes dozens of the best candidate images from every future job, and there's no reset besides deleting pool.sqlite. · This silently degrades coverage and pool data over time. · Fix: only mark an image bad for definitive outcomes (HTTP 4xx, undecodable image, `validate_photo` failure). Return a distinct result for network failure. Alternatively, make `is_bad_image` ignore network-type marks older than N days, using the existing `at` column.
5. studio/pipeline.py:506-526, 606-638; studio/zomato.py:332-356, 252-299 · `source()` and `search()` only catch `ZomatoBlocked`, so any other discovery exception aborts the whole job. Examples: `requests.TooManyRedirects` / `ContentDecodingError` from `Http.get` (only ConnectionError, Timeout and ChunkedEncodingError are caught at zomato.py:146), `AttributeError` in `suggest` when the JSON isn't a dict, and `AttributeError` in `parse_menu` when `item_entry["item"]` is None (only KeyError and TypeError are caught). A resume hits the same error again. · This violates AC7 ("one dish's failure never aborts a job"), and R6 says a page-format change should degrade, not crash. · Fix: wrap the vendor lookup in `source()` and each `cached(...)` call in `search()` with `except Exception: log.warning(...); continue`. Also catch `AttributeError` in `parse_menu` and `requests.RequestException` in `Http.get`. Add a test where a fake client's `suggest` raises `ValueError` and the job still finishes `done`.
6. studio/vision.py:186-204 + studio/pipeline.py:724-726 · The close-tier "consensus >= 0.5" gate can't reject anything. `consensus()` returns 1.0 for one candidate and 0.5 for two identical-weight candidates. For three or more it min-max normalises, so the top candidate always scores 1.0. A lone close-tier match (only soft tokens missing, e.g. "Chilli Paneer Dry" vs a gravy item) therefore passes as if photos agreed. · This is a precision gate that looks real but doesn't work (priority 1). · Fix: compute the gate from the raw weighted mean cosine (before normalising) against an absolute threshold, and/or require at least 2 close candidates from different restaurants that agree. Add a test where a lone close candidate with no agreeing photo ends as needs_photo in balanced mode.
