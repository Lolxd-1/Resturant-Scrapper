## Implemented
- New file `studio/matcher.py`. It provides `PoolIndex` (`add`, `idf`, `retrieve`, `__len__`, `item_tokens`, plus `median_idf()`), `score`, `rank` and `same_dish_menu_match`, following the Contracts.
- Item facts are computed once per (name, category, menu_name) and cached (`lru_cache`, 65,536 entries):
  - tokens(name)
  - item_head(name, category, menu_name)
  - item_proteins(name), falling back to item_proteins(category) when the name has none
  - is_combo_name(name)
- When the head comes only from the category (the name has no head token), the head token is added to the item's match tokens. Without this, "Peppy Paneer" in "Veg Pizza" would be rejected as "missing PIZZA", and TC-same-menu needs it to match.
- `score` runs these checks in order: empty, diet, protein, combo. It then scores each variant and keeps the best. If every variant is rejected, it returns the reject from variants[0].
- The head gate is evaluated per variant. A variant's head is q.head only if that variant contains a token whose head is q.head; otherwise it is None. This is needed for P3: in "Flower Masala (Cauliflower Curry)", q.head is CURRY, which comes from the parenthetical, while the main variant {GOBI, masala} has no head.
- Text score = tier floor + bonus − penalty, clamped to the tier range:
  - Bonus: token_set_ratio × 0.10 for exact/strong, × 0.14 for close.
  - Penalty: 0.01 for each extra nonvisual or soft token.
  - Tier ranges: exact [0.90, 1.0], strong [0.75, 0.8999], close [0.55, 0.7499].
- `retrieve` works like this:
  - It unions the postings of the query's variant tokens with df ≤ 25% of N (rarest first) and weights each item by the summed idf.
  - It adds the head postings unless they were already counted. Items that already have an overlap get extra weight; head-only items are capped at limit×3.
  - It applies the diet pre-filter, then takes the top `limit` with `heapq.nlargest`. Ties go to the lower position.
- `same_dish_menu_match` returns the best exact or strong result from `rank`. Otherwise it returns the item with the highest token_sort_ratio ≥ 92 and the same head, as tier "strong" with text 0.75 + 0.10 × ratio.
- `studio/text.py` (ruling from the T03 Notes): the dish name now decides diet first.
  - Proteins → nonveg or egg.
  - A nonveg hint in the name → nonveg; a veg hint in the name → veg.
  - A category nonveg hint counts only when the category has no veg hint (after removing "non veg"/"non vegetarian") and the name has no base token.
  - A category veg hint counts only when the category has no nonveg hint.
  - Otherwise the diet is unknown.
  - "Dal Fry" alone is still "unknown", so the existing TC9 passes unchanged. A base token alone does not make a dish veg; it only blocks the category nonveg hint.
- Lexicon changes: none. `studio/lexicon.py` is unchanged.

## Concerns
1. `score()` receives only an idf Callable, so it has no direct access to the "pool median idf". The median is read from the owning PoolIndex when `idf` is a bound `PoolIndex.idf` (`idf.__self__`). For any other callable, there is no median, and every extra visual token rejects (the safe direction).
2. I defined the median as occurrence-weighted: half of all item-token occurrences are at least this common. A median over distinct tokens would put almost any repeated word (e.g. "mango", df ≥ 2) below the median. Then N30 (Lassi vs Mango Lassi) would become close in any realistic pool. With my definition, N30 rejects in the test pool (mango idf 4.87 > median 4.47). In a real 400k pool, very common flavour words (e.g. "cheese", maybe "chocolate") could still fall below the median and allow "X" → "Chocolate X" as close. Consider dropping the exception if precision matters more.
3. The rule "q.is_combo and the item is not a combo → at most close" almost never fires. Combo words ("combo", "meal") are ordinary visual tokens, so they show up as missing and the item is rejected. With two heads, the second head also shows up as missing. The rule fires only when "plus" (a noise word) marks the combo. The result is safe but strict.
4. PoolIndex postings use name tokens only (Step 1). Items whose head exists only in the category ("Margherita" in "Pizzas") are therefore found through their other tokens, not through q.head postings.

## Discoveries
