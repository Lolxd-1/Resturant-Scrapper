# T14 report: Seed pool builder tool

## Implemented
- `tools/__init__.py` (empty, makes `tools` importable).
- `tools/build_seed_pool.py`:
  - `import_cache(store, cache_dir) -> int`: reads every `*order.html` in a cache dir, `parse_state` -> `parse_menu(state)` (no fallback_url; per brief, filename-derived URLs are unreliable), `store.upsert_menu`, returns total items imported.
  - `import_pairs(store, pairs_path) -> int`: groups legacy `{"name","img","rest"}` rows by `rest` slug, skips any slug whose restaurant already exists in the store (checked via `res_url.endswith("/" + slug)` over `store.all_items()`), upserts the rest as `RestaurantMenu(res_id="legacy-"+slug, url="https://www.zomato.com/legacy/"+slug, city="legacy", ...)`. Diet comes from a new private `_legacy_diet(name)` keyword rule (chicken/murgh/mutton/fish/prawn/keema/meat -> nonveg; egg/anda/omelette -> egg; else unknown) per the orchestrator's override — `studio/text.py::item_proteins` does not exist yet (T03 lands later).
  - `crawl(store, client, cities, cuisines, max_restaurants, workers, log=print) -> int`: for each city x cuisine, calls `client.listing`, dedupes URLs already seen this run or already fetched (`store.menu_fetched_at`), fetches new ones with `ThreadPoolExecutor(workers)` via a `_safe_fetch` wrapper that turns `ZomatoBlocked` into a sentinel, upserts menus, logs progress every 25 restaurants, stops once `max_restaurants` new restaurants are fetched. First `ZomatoBlocked` (from `listing` or a fetch) logs "Blocked by Zomato; waiting 10 minutes", sleeps 600s (`time.sleep`, monkeypatchable), and continues; a second block returns cleanly without raising.
  - `export_seed(store, out_path) -> dict`: streams restaurants with >=1 imaged item, sorted by `res_url` (items sorted by `(category, name)`), into gzip (compresslevel 9) JSONL with keys `r, rn, c, n, cat, m, d, dt, i` (`d` truncated to 200 chars); returns `{"restaurants","items","bytes"}` and prints them.
  - `main()` wires an argparse CLI matching the brief's contract; no flags prints help.

## Concerns
- TC3's real listing regex (`studio.zomato._extract_res_urls`) matches on `/{city}/{slug}/(info|order)`, so a restaurant literally cannot share the same canonical URL across two *different* city arguments (the href's city segment must equal the loop's city). To faithfully exercise `crawl`'s own dedup/threading/stop/blocked logic (rather than re-testing `zomato.py`'s regex, already covered in `tests/test_zomato.py`), I used a small duck-typed fake client (`_FakeCrawlClient`) implementing `.listing()`/`.fetch_menu()` instead of `FakeSession`+`Http`+`ZomatoClient`. Real `ZomatoClient`/`Http` are still exercised by `main()` and unit-tested elsewhere; nothing in `crawl()` depends on the concrete client type beyond those two methods.
- `import_pairs`'s "already exists" check loads `store.all_items()` into memory once; fine at this scale (matches the store's existing `all_items()`-based access pattern), but would be a full scan for a very large store.

## Discoveries
- `data/pairs.json` legacy entries carry no restaurant city, so legacy-imported restaurants all land under a synthetic `"legacy"` city segment (`https://www.zomato.com/legacy/<slug>`) — later tasks that filter/display by city should be aware of this bucket.
- `studio/text.py` (and `item_proteins`) still does not exist; `_legacy_diet` in `tools/build_seed_pool.py` is a standalone keyword rule that should probably stay until T03 lands, at which point the orchestrator may want to reconcile the two diet-inference paths.
