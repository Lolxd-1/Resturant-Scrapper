## Implemented (studio/pipeline.py)
- JobOptions, JobCancelled, Engine (store/vision/http/client/index/blocked, add_menu), build_engine, new_job_id, load_job, list_jobs, infer_category, run_job.
- Stages in order: read, source, match, search, verify, photos, upload, build. Stage state lives in a private `_Run` class. Rows are grouped by base_key; an empty base_key (a non-English name) gets its own group `#<row>`, so unrelated Devanagari dishes never share a group.
- Source: zomato_url gives "own". Otherwise, if the pool already has 3 or more restaurants with the vendor's chain_key, those items are used as a "chain" source with no fetch. Otherwise the job tries suggest in up to 4 cities (chains, then same-name restaurants). Matching against the source menus uses same_dish_menu_match with the bound engine.index.idf.
- Search: up to 3 city-slice rounds. suggest/listing results are cached per job. Each round's targets are interleaved round-robin across groups before the budget cap is applied (my choice; the brief only says "until the budget is used"). Menus are fetched on 4 threads, add_menu runs on the main thread, all unresolved groups are re-ranked after each batch, and ZomatoBlocked sets engine.blocked, logs BLOCKED_MESSAGE and ends the stage. Groups whose name has no English variants are skipped here (the query would be empty).
- Verify: implements vision scoring, the text-only fallback, strictness, the big-brand penalty, distinct images, alternates and the needs_photo reasons, all as the brief states. results.json is written after the stage.
- Photos: tries the pick and then the alternates. A failed download is marked bad. Resume reuses old image and hosted_url when zomato_img matches and the file exists.
- Upload: one call per group. With no uploader, or a "No ImgBB API key" error, the remaining groups are stopped. Checkpoint after each group.
- Each dish event is emitted once per row, when the row is final (in the photos stage, or in the upload stage when uploading).
- Cancel is checked at each stage start, between groups, and between menu-fetch completions.
- summary["files"] holds file NAMES relative to job_dir, not full paths.

## Concerns
1. BUG in studio/sheets.py (T09, outside my write-set): openpyxl `ws.cell(row, col, value=None)` does NOT clear a cell. So `_clear_rows` is a no-op, and `_write_rows` never blanks a cell for a None value. PENDING rows therefore keep stale READY values in E/F (price), I (description) and P (photo URL). Seen in TC1: PENDING P3 ("Ceet-B Mastani", no photo) showed READY row 2's URL. Fix: assign `ws.cell(row=i, column=c).value = v`. I dropped my `P3 is None` assertion because it is outside this task.
2. add_menu follows the contract (store.items_for_restaurant → all_items reload). With the real seed (137,893 items) each reload takes about 0.5 s, so a full 250-menu live budget adds about 2 minutes. Cheaper option: index.add the menu's items directly, or give the store an items-by-res_url query.
3. build_engine's `settings` parameter is unused (the contract lists it, but nothing in Settings configures the engine).
4. engine.blocked is never reset. A long-lived server engine skips live search in every later job once Zomato has blocked it.

## Discoveries
- summary["files"] values are file names inside job_dir.
- In a tiny pool, PoolIndex.retrieve drops tokens whose df is above 25% of items, so tests with a very small pool need filler items (see TC6).
